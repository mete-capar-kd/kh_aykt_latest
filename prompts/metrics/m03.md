# m03 — Uygulama Güvenliği ve Secret Yönetimi

## Amaç

Uygulama güvenliği kontrollerini ve secret yaşam döngüsünü, hassas değeri açığa çıkarmadan doğrulanmış kod kanıtıyla değerlendirmek.

## Kontrol kapsamı

- Hardcoded secret
- API key
- connection string
- Key Vault kullanımı
- input validation
- SQL Injection
- CORS ayarları
- güvenlik headerları
- hassas veri loglama ve güvensiz şifreleme yöntemleri

## Kabul kriterleri

- güvenlik açığını doğru sınıflandırmalı
- secret değerlerini raporda açık göstermemeli
- kanıtı dosya/satır bilgisiyle sunmalı
- güvenli alternatif önermeli
- kritik bulguları yüksek öncelikle raporlamalı.

## Tipik ihlaller

Kaynakta credential, birleştirilmiş SQL, sınırsız CORS, doğrulanmayan girdi, hassas log alanı ve güncel olmayan kriptografi tipik adaylardır.

## Meşru istisnalar

Placeholder, test fixture, public identifier, maskelenmiş örnek veya parametreli sorgu güvenlik açığı olmayabilir. Bulgu öncesinde değerin ya da kullanımın neden meşru olabileceğini değerlendir ve `rationale` alanına yaz.

## Kabul edilen kanıt

Maskelenmiş dosya-satır snippet'i, veri akışını gösteren çağrı bağlamı, güvenlik yapılandırması ve doğrulama/saklama entegrasyonu kabul edilir.

## Belirsizlik ve yetersiz kanıt

Değeri secret sanarak rapora kopyalama. Tür veya akış doğrulanamıyorsa kesin hüküm verme; `Kanıt yok` ya da `potansiyel` kullan.

## Kesin / potansiyel

Doğrudan sömürülebilir veri akışı görülüyorsa `kesin`; runtime veya dış config doğrulaması gerekiyorsa `potansiyel` kullan.

## Metriğe özel davranış

Secret değerlerini daima maskele. `standardRef` değerini `UseCase §6.3 — <alt kontrol>` biçiminde yaz. Severity sınıflandırmasını erişilebilirlik ve etkiye dayandır; güvenli alternatif teknik ve uygulanabilir olmalıdır.
